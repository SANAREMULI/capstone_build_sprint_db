# Lessons Learned

Building ShopSphere made the relationship between database design and operational behavior much clearer. The first lesson was that a tenant identifier is not just a column added for filtering. It is a boundary that must travel through keys, joins, indexes, session context, policies, audit records, and backup procedures. Composite foreign keys made that boundary explicit. They also exposed how easy it would be to create a valid-looking relationship that accidentally connected rows belonging to different merchants.

The second lesson was that normalization and performance are not opposites. Orders, products, inventory, and payments remain separate because each has a different lifecycle and consistency rule. Performance came from indexes that match the actual access pattern: tenant plus time for reports, tenant plus customer plus time for order history, and a partial index for low stock. The explain-plan comparison made this concrete. A sequential scan may be acceptable for a tiny demo database, but the same plan becomes an operational problem as data grows.

The NoSQL exercise improved my judgment about where relational guarantees are necessary. Redis is a good fit for carts because carts expire, change frequently, and can be rebuilt. MongoDB is useful for activity events because their metadata can evolve independently from the order schema. Neither should become a second source of truth for completed purchases. Keeping PostgreSQL authoritative avoids split-brain checkout behavior and makes recovery easier to reason about.

Security also became more practical when implemented as separate controls. Roles limit what a connection can do, RLS limits which tenant rows it can see, parameterized queries limit injection risk, and audit triggers provide accountability after a change occurs. These controls overlap, but they do not replace one another. A read-write role without RLS would still be too powerful; RLS without audit history would make investigations harder.

The most useful operational practice was treating backup as a tested workflow rather than a successful command. A dump that cannot be restored is not a backup. The custom-format dump, checksum, disposable restore database, and table-count verification create evidence that can be repeated. In a production system I would extend this with encryption, off-host retention, alerting, and scheduled restore drills.

Overall, I gained stronger skills in relational modeling, PostgreSQL migrations, indexing, query plans, RLS, audit design, Redis data modeling, MongoDB event storage, and recovery planning. I also learned to document assumptions and limitations honestly. The next step is to automate these checks in CI so the database remains verifiable as the application evolves.
